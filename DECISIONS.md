# Decisions

This document records the resolved design decisions for banksman. Each entry states the
**provisional** decision and its rationale. Every decision is reversible; the last column
says what changing it would involve. The full design is in [docs/DESIGN.md](docs/DESIGN.md).

| # | Decision | Provisional choice | Rationale | How to change |
| - | -------- | ------------------ | --------- | ------------- |
| 1 | Name and packaging | `banksman`: PyPI package, import package, and console script | One name for the tool and its command. | Rename the package directory, the `pyproject.toml` entries, and the configuration paths in one change. |
| 2 | License and contributions | Apache-2.0, DCO sign-off | Permissive, with a patent grant. DCO avoids a CLA. | Relicensing needs every contributor's consent. Decide before accepting outside contributions. |
| 3 | Runtime | Python 3.11+, standard library only | `fcntl`, `json`, `tomllib`, `subprocess`, and `argparse` cover the need. A tool that other tools call from their scripts must install with no friction and a small supply chain. | Add a dependency only with a justification in the PR; keep test-only dependencies separate. |
| 4 | Platform | macOS first; Linux expected to work | The core uses POSIX primitives only: file locks, process groups, signals. CI runs both. | A platform without `flock` and process groups needs its own implementation of the lease store. |
| 5 | Leases, not locks | Every hold expires: owner gone, idle, or past a hard cap | A lock held by "whoever started it" stays taken forever when that run dies. | n/a: this is the point of the tool. |
| 6 | State | One lease file per resource in a fixed per-user directory, `/tmp/banksman-<uid>`; bookkeeping under a file lock held for milliseconds; a quarantined lease also outside `/tmp` (#20) | The kernel releases the lock when its holder dies, so there is no stealing logic. No daemon has to stay alive. The path does not come from `$TMPDIR`: callers of one user can have different values, and would then not exclude each other. | A daemon could hold the state in memory, but it would add a process that must survive everything the leases survive. |
| 7 | Interface | A command with `KEY=value` and JSON output, versioned by a `schema` number; no library API | Project scripts, build hooks, and other tools all call the same command, so a machine has one lease implementation. | A library API needs a promise that it and the command never disagree about the lease files. |
| 8 | Kinds | Declared in configuration: counted, or named with a list of instances or with a `discover` hook; with their own timeouts, a rank, and `on_acquire` and `on_void` hooks | A new kind of resource needs configuration, not code, and the reaper has no branch for a specific kind. | Presets for common kinds ship with the tool; they are configuration too. |
| 9 | Access | An allowlist that is closed by default; `discover` is a human gate; no default pattern | A machine with test devices usually has something personal on it too. Excluding a test device by mistake costs one re-scan; including a personal one gives an agent real credentials. | Only the operator widens access, never a request. |
| 10 | Requests | By properties: one or more parts (#33), each an AND of clauses on facts from discovery, on the attributes that banksman sets itself (`kind`, `account`, `tag`), and on tags from the operator; an unknown attribute is an error | A run knows what it needs, not which device has it. A hook cannot set the attributes that decide access, so it cannot make an instance look like one with an allowed account. | New facts come from a kind's `discover` hook. |
| 11 | Holder identity | Derived from facts every caller has: worktree, issue id, and the nearest known agent process. The worktree is only the readable name of the owner: the lease id identifies a holding (#27) | It must work for any agent and for a person, and a caller cannot forget it. Several agents can work in one worktree at the same time, so the worktree cannot tell their holdings apart. | Agent-specific values are optional extras, never required. |
| 12 | Scope | banksman knows devices, their facts, and leases, and nothing about any app | App setup, app data, test accounts, and app ports differ in every project and belong in that project's scripts. | n/a: an app-specific need goes into the project's scripts or a hook. |
| 13 | Operator commands | All under `banksman admin` | An agent's permission rules can refuse every operator command with one pattern, including ones added later. | n/a. |
| 14 | Optional use | A project's scripts check for the command and behave as before without it | A silent dependency would break the machine of every developer who does not install it. | n/a. |
| 15 | Time | Lease deadlines count awake time (the monotonic clock) on one boot, identified by the boot session id | With wall-clock time, a laptop that sleeps finds every lease void when it wakes, and the reaper takes resources from runs that are still alive. A change of the wall clock does not move a deadline either. | Store wall-clock deadlines instead. That changes the lease file format, so raise the `schema` number. |
| 16 | Stopping processes | Off by default: the reaper sends no signal unless the operator turns stopping on for a kind. Even then it signals only processes that the lease's owner process started, so without a known owner process it signals nothing | banksman must never stop a process that the user did not expect, whatever agent the user runs. A blocked device costs time; a stopped process costs trust. A script can register a process that it did not start, such as its agent, and banksman cannot detect that without knowing the owner process. | Turn it on for a kind in the configuration with `stop = true`. The reaper then stops only registered scripts and the processes they started, never their parents. |
| 17 | Ending an instance | The reaper ends a void instance, for example kills an emulator, only through the kind's `on_void` hook, and that hook runs only if the operator declares it. banksman ships none. | Ending an emulator that banksman leased is much less risky than signalling processes, so it is a separate choice from #16. A kill alone is not a fence: the next instance can get the same address, so the resource is freed only after the registered scripts have also ended. | Declare or remove the hook for the kind. |
| 18 | Configuration file | `~/.config/banksman/config.toml`; the home directory comes from the user database, not from `$HOME`, and `$XDG_CONFIG_HOME` is not used | The reaper takes resources back with the hooks in this file, so every caller of one user must read the same file, for the same reason as the fixed state directory (#6). | Read the path from the environment. Then two callers can take back one resource in different ways. |
| 19 | Hooks at take-back | The reaper reads the kind's `on_void` hook and `stop` setting from the current configuration; a lease keeps its own timeouts | When the operator removes a hook that kills, or turns stopping off, it must stop at once, also for void leases that the reaper has not taken back yet, and a corrected hook applies to those leases too. A lease that a failed hook already quarantined waits for a person. The void rules still need no configuration. | Copy the hook into the lease when it is granted. Then the reaper needs no configuration, but a change applies only to new leases, and the lease file format changes. |
| 20 | Quarantines outside `/tmp` | A quarantined lease is also kept in `~/.local/state/banksman/quarantine`, with the home directory from the user database; every command first restores a quarantined lease file that has gone from `/tmp` | Cleaners of temporary files delete old files in `/tmp`, on macOS every night for files older than 3 days, and macOS empties `/tmp` at boot. A quarantine must last until a person releases it, also across a restart, so that the take-back after a restart runs. Active leases stay in `/tmp`: they change often, and they need no copy. | Refresh the times of quarantined lease files at every reap instead. That needs no second directory, but a quarantine is then lost after 3 days without a banksman command, and at every restart. |
| 21 | Fencing token | Scripts pass the lease id to `enter`, `check`, `leave`, `touch`, and `release` | A script of an earlier lease, for example one of the same worktree, must never act on a newer lease of the same resource. The owner alone cannot tell the two leases apart. | Check the owner instead. Then a script of an earlier lease of the same owner passes the check. |
| 22 | Scripts that do not stop | A void lease waits for its scripts until its drain deadline (`drain_timeout`, 5 minutes by default), and is then quarantined. The quarantine stays after the scripts end. A release while scripts still run drains the lease too | The resource is never handed on while a script of the earlier holder can still use it. A person sees why a script did not stop before the resource is used again. | Free the resource automatically when the scripts of a quarantined lease end. Then a person never needs to act, but also never sees the scripts that did not stop. |
| 23 | Finding the worktree and the branch | Read the files: the owner is the nearest directory with a `.git` entry, from the working directory up, and the branch comes from the `HEAD` file. banksman runs no `git` process | It works when `git` is not on the caller's `PATH`, and it costs no extra process for each command. A linked worktree and a submodule have a `.git` file, which ends the search, as for `git rev-parse --show-toplevel`. | Run `git rev-parse` instead. That also follows `GIT_DIR` and other git settings, but it adds a process and depends on the caller's `PATH`. |
| 24 | Finding the agent | The nearest ancestor process whose executable name is in the configured `agents` list, `claude` and `codex` by default. Case matters | Every caller has a process ancestry, so it works for any agent and needs no flag. The nearest agent is the one that runs the command, also when one agent runs another. The Claude app's own executable is `Claude`, which is not the agent. | Add a name to `agents` in `[holder]`. An agent that runs its commands outside its own process tree needs `--owner-pid`. |
| 25 | The inventory and its refusals | `admin discover` writes `~/.config/banksman/inventory.toml`, and the configuration stays read-only. Only a person refuses: in the interactive mode, a name that is left unselected is refused, and a refusal wins over patterns and `--all`, also for every other kind. With `--yes`, an unselected name gets no decision | A new scan can never silently widen access to a name that a person refused, and a pattern that the operator adds later still selects a name that nobody refused. | Refuse every unselected name also with `--yes`. Then a pattern added later never selects a name that an earlier unattended scan saw. |
| 26 | The Android SDK of the presets | A fixed place in the home directory from the user database, or `sdk` and `avd_home` in `[android]`; never `$ANDROID_HOME` or `$ANDROID_AVD_HOME` | Every caller must see the same devices and emulators, for the same reason as for the state directory (#6). | Read the environment. Then two callers can see different devices. |
| 27 | Keeping a lease | `acquire --lease <id>` keeps the caller's leases with that id whose resources still match (#34); without it, `acquire` never grants a held resource, also not to the same worktree. `touch` and `release` take the lease id, and `release --all` gives back only the leases of the caller's agent process | Several agents can work in one worktree at the same time, and only the lease id and the agent process tell them apart. The caller already keeps the lease id for its scripts (#21). | Grant a held resource again to the same owner. Then two agents in one worktree get the same resource without knowing it. |
| 28 | Order of choice | The caller's kept lease, then the kind with the lowest `rank`, then an instance that runs before one that does not run, then the resource name. `acquire` grants one resource for each part of the request (#33); it never returns a list to choose from. The `android-device` preset has rank 1, and every other kind 0 | Physical devices are usually scarcer than emulators, and the start of an emulator costs time and memory but no scarce resource. A fixed order is predictable and can be tested. Two callers that choose from the same list choose the same resource; an agent that needs a specific one asks for it with a clause. | Set other ranks in the configuration. An order by recent use or by load needs state that banksman does not keep. |
| 29 | Instances that do not run | banksman starts nothing. Every grant is `ready`, and the holder starts an instance that does not run. The `running` fact only orders the matches. There is no `reserve` and no `ready` command | Discovery can be wrong, for example about an emulator that is still starting, so the holder must check anyway. A wrong `running` value then costs only a worse choice, never the start of an emulator that already runs. | Grant a `booting` lease for an instance whose `running` fact is false, and add `ready` for the holder to run after the start. The boot deadline then frees a resource whose start never completes, but a wrong fact makes the holder start an instance that runs. |
| 30 | A failed `on_acquire` hook | The lease is given back, and `acquire` fails. The instance is not quarantined | A failed reset does not make the instance unsafe for the next holder, as a failed take-back does (#17). A quarantine would need a person also for a failure that does not happen again. | Quarantine the instance. Then a person sees every failed reset, and later requests do not choose the same broken instance again. |
| 31 | Waiting | `--wait` looks again every 5 seconds, without a queue. A request that no permitted resource that is present now matches fails at once, also with `--wait` | Without a daemon, nothing hands a freed resource to the next caller, and a queue across requests that match different resources needs a design of its own. Waiting helps only while a matching resource is held. | Add a queue of the callers that wait, in the state directory, so that the earliest caller gets a freed resource first. |
| 32 | A reset and a take-back never overlap | The lease names the `acquire` that runs the `on_acquire` hook, in the fields that name a reaper. A lease that becomes void or is released during the reset drains, and it is taken back or freed only after that process has ended. `admin release --force` refuses meanwhile | A hook ends with the process that runs it, so the end of that process proves that the reset has ended. Without this, a short timeout or a release during the reset could hand the instance to the next holder, or run `on_void` on it, while the hook still acts on it. | Make the boot deadline of a reset at least the hook timeout instead. That covers only the boot deadline, not the other void rules or a release. |
| 33 | Several resources at once | One `acquire` with parts (`--as <name>`), granted all or nothing under the lock. Each part takes its matches in the order of choice, an earlier part first, but it takes a later match when a later part can get nothing else. A request that could not be met even with every resource free fails at once. The search stops after 1 second | Two runs that each hold one resource and wait for the other would deadlock. A choice part by part in the order of the parts could wait for a request that another choice meets at once. Other commands wait at most 10 seconds for the lock, so the search must stay short. | Choose part by part in the order of the parts. The search is then simpler, but some requests that can be met wait until `--wait` ends. |
| 34 | One holding for each acquire | Each lease has its own id, and the leases of one `acquire` form one holding. `check`, `enter`, and `touch` touch every held lease of the holding. The id of any lease names its holding for `acquire --lease`, `touch --lease`, and `release --lease`. The new leases of a request with `--lease` join that holding while it has a held lease, each with a new id | A run uses its resources together, but a script checks only the resource that it uses: a tablet must not time out while a long test runs on the phone. A resource that joins a holding again must get a new token, so that a script or a cleanup of its earlier lease never acts on the new lease (#21). | Give the leases of a holding one shared id. The scripts then need one token only, but an earlier lease of a resource that joins the holding again has the same token as the new one. |
| 35 | Accounts | An account is leased with its device: the device lease lists it in `accounts`, and no request gets an account while a lease in any state lists it. Lease files carry the accounts, so their schema is 4 | The account must stay in use exactly as long as the holder can still use it through its device: also while the lease drains or is quarantined, and without a touch of its own. An account lease of its own would time out while the scripts touch only the device, and it would be freed while the scripts of a draining device lease still run. | Give each account its own lease file with a link to its device lease. An account could then also be leased without a device, but the reaper needs rules for leases that follow other leases. |
| 36 | Granting accounts | `--accounts N` grants N allowed accounts that are signed in on the granted resource now, in the order of their names, and names them in `ACCOUNTS`. It never returns the list to choose from | Two clients that choose from the same list choose the same account. | Also return the list, for information. A client could then still use an account that it did not get. |
| 37 | Resets in a joint request | While a request has resets, every new lease of the request is `booting` and names the `acquire`. The resets run one after another, and each boot deadline also counts 60 seconds for each reset of the request. At the end, every new lease must still be held; otherwise all of them are given back | Another process must not free a lease of one part, for example one that became idle, and hand it on while the `acquire` still resets another part. A later reset must not miss its deadline because earlier resets ran first. | Run the resets at the same time. That takes less time, but an `acquire` that is interrupted must then wait for every hook before it gives the leases back. |
| 38 | What `status` shows | Every resource that the configuration declares or the inventory allows, present now or not, and every resource that has a lease file, but never a discovered instance that the inventory does not allow. `status` and `watch` run discovery | A person and an agent must also see the free resources, to know what they can ask for, and an allowed instance that is not present, such as an unplugged phone. A discovered instance that nobody allowed can be personal, and agents read `status`. | Show only the leases. `status` then needs no discovery and is faster, but it shows no free resource. |
| 39 | "Free by" | Three labeled values: expected (the holder's `--expect`), at the latest (the hard cap), and if abandoned (the earliest time at which the lease is void without another touch). The table shows times of day; the JSON also gives seconds from now | banksman cannot know when a holder gives a resource back. Only the hard cap is a promise, and the other two values are what a caller needs to decide whether to wait. The deadlines count awake time (#15), so seconds from now stay correct when the machine sleeps, and a time of day moves later. | Show one estimate. That is simpler, but it hides which part is a promise. |
| 40 | The log | An append-only file of JSON lines, `~/.local/state/banksman/log.jsonl`, written under the lock of the lease store; at 10 MB a new file starts and one earlier file is kept. A release and a void record the held time and the longest time between two touches, so lease files carry `awake.acquired` and `longest_quiet`, and their schema is 5. A log that cannot be written does not fail a command | The history must outlive restarts and cleaners of `/tmp` (#20). The two durations are the measurements for the hard cap and the idle timeout; an event for every touch would grow the log with every check loop. A change to a lease that is already written must not fail because of its history. | Record every touch. The log then has every gap between touches, but it grows with every check loop. |
| 41 | Build slots for Gradle | A Gradle init script, which `banksman admin gradle-init` prints, takes a slot of the kind `build` when each build starts and gives it back when the build ends. Its owner process is the process that runs the build, usually the Gradle daemon | An init script covers every build, also one that an agent starts directly, without a wrapper. The daemon does not know the process of its client, and it runs one build at a time. With `owner_grace = "0s"`, the slot is free as soon as the daemon ends. banksman does not write into `~/.gradle`, which belongs to Gradle and to the operator. | Wrap the `gradlew` command instead. The client could then be the owner, but a build that does not go through the wrapper takes no slot. |
| 42 | The Gradle hooks | The slot is taken in a `ValueSource` of the build-slot part (#45) and given back when a build service of that part closes. The script keeps no lease id: before it takes a slot, and when the build ends, it gives back every lease whose owner process is its own process | An init script does not run when Gradle reuses the configuration cache, but Gradle runs its value sources again before it reuses an entry, before any task. When an entry is stale, the value source runs twice in one build, in two class loaders, so no memory of the process can hold the lease id. A `FlowAction` needs Gradle 8.1 and is incubating, and an init script that does not compile fails every build of the user. The cost: a build that runs no task while Gradle reuses the cache, such as `--dry-run`, keeps its slot until the next build of its daemon, the end of the daemon, or the hard cap. | Give the slot back in a `FlowAction`, which also runs when no task runs. Then the script needs Gradle 8.1, and a change of that incubating API fails every build. Or keep the lease id in a file for each daemon: a second run in one build then keeps its slot instead of taking it again, but the script must manage those files. |
| 43 | A build without a slot | A build that gets no slot within its wait fails, with a message that says that this is a limit of the machine. Any other error of banksman fails the build too. Without `banksman` on the `PATH`, the script does nothing | A build that ignores the slots uses the memory that they protect, and a wrong configuration must not go unnoticed. A machine without banksman builds as before (#14). | Warn and build without a slot. Builds then never fail because of banksman, but a wrong configuration lets them use up the memory. |
| 44 | Waiting, and the owner process | `acquire --wait` says once on standard error that it waits, with the resources in use. It stops waiting, and fails, when its owner process ends | A person sees why a command, such as a build, does not go on. Nothing would use what an ended owner gets: a Gradle daemon that stops while its build waits would leave its `acquire` behind for the rest of the wait. | Wait to the end in any case. The grant then fails, or the reaper frees it at the next command. |
| 45 | The Gradle script in two parts | The init script in `~/.gradle/init.d/` uses only APIs that old Gradle versions also have. On Gradle 7.4 and later, it applies the build-slot part, which the operator saves in `~/.gradle/banksman/` with `gradle-init --build-slot`. On an older Gradle, a build runs as it does without banksman. When the build-slot part is missing, the build fails | The init script applies to every build of the user, also in projects on an old Gradle. Gradle compiles a whole script before it runs any of it, so a check of the version inside the build-slot part comes too late. Gradle 6.5 to 7.3 also need `forUseAtConfigurationTime()`, which Gradle 9 removed, and Gradle 6.9 has not loaded the Gradle properties yet when an init script runs. A file that the operator saves needs no process while Gradle configures a build: with the configuration cache, Gradle 7.5 and later fail a build that starts a process then. A missing build-slot part fails the build, because a build that ignores the slots uses the memory that they protect. | Apply the build-slot part from the installed package, at a path that the `banksman` on the `PATH` prints. The operator would save one file once, but the init script would need `providers.exec`, which Gradle 7.5 added, and the `PATH` would become an input of the configuration cache. Or support Gradle 6.5 to 7.3 with code for each version in the build-slot part. |
| 46 | A supervised run | `banksman run` runs a command in a new process group under a leader program that banksman starts. The leader and its group are registered with the lease before the command starts. The lease is checked every 10 seconds, or every quarter of its drain timeout or idle timeout when that is shorter. A lost lease stops the group, SIGTERM and then SIGKILL, and `run` leaves only when no process is left in the group. `run` exits with the status of the command, or with 3 when the lease is lost, also when the command fails after the lease was lost. When `run` ends first, the leader ends the group | A shell script cannot easily create a process group, because macOS has no `setsid` command, and the check loop, the stop, and the wait for the group are easy to get wrong in each project. The leader lives until `run` is done with the group, so the id of the group never names another group when `run` signals it; `waitid`, which could watch an ended leader without reaping it, is not available on macOS before Python 3.13. A command must not run without its check loop, as a hook must not outlive its reaper. Status 3 is the status of `check` for a lost lease. | Each project writes the loop with `enter`, `check`, and `leave` itself. Or `run` uses a status for a lost lease that a command is less likely to give by itself, such as one above 100; a script then needs another number for a lost lease than for `check`. |
| 47 | A run that leases its own resource | `run --where` leases one resource for its command, with `run` itself as the owner process, and releases it after the command. A counted kind with `count = 1` is then a mutex for one command at a time. A lease whose owner process runs and started the caller keeps that owner when the caller keeps or touches it | The lease must end with the run, also when something kills the run. With the agent as the owner process, it would stay until its idle timeout, and so would it if a script inside the run, which keeps the lease of the run, moved it to the agent. After a restart of the agent, the earlier owner has ended, so the new agent process is still recorded. | Make the agent the owner process. A killed run then holds the resource until the idle timeout. |
| 48 | The helper of a project | A POSIX `sh` helper, and a stub of `banksman` for tests, in the documentation. A project copies them into its repository; banksman installs neither. A lease that `acquire` keeps for a script stays with the caller; `acquire` prints `KEPT` for each part, so the helper does not compare lease ids | A project must work the same on a machine without banksman (#14), so its scripts cannot source a file that banksman installs. A script that gives back a lease that its caller holds would take the resource from the caller, for example from a `banksman run` that runs the script. A kept lease can have another id than the one that the caller gave: each lease of a holding has its own id. | Ship the helper in the package, and let scripts find it with a command. A machine without banksman then has no helper, and every script needs a branch for that. |
| 49 | The serial in a lease | A lease records the serial of its instance, from discovery only, never from the holder. Every command that runs discovery (`acquire`, `run`, `status`, `watch`) records what it finds in the held leases of the kind: a serial that discovery reports is set, an instance without a serial that does not run loses it, and in every other case the lease keeps it. A result does not apply when the lease records a discovery that started later, and a serial belongs to one held lease at most, also when discovery finds it on an instance without a lease. `run` gives its command only a serial that its discovery confirms before the command starts, a reset keeps no serial that discovery does not find after it, and `on_void` gets the serial that discovery finds at the take-back. Lease files carry `serial` and `awake.serial_seen`, so their schema is 6 | `run` and the hooks act on the serial, through `BANKSMAN_SERIAL`, `ANDROID_SERIAL`, and `{serial}`. A serial that the holder reports can be wrong, for example after two emulators started at the same time, and a wrong one sends commands to the device of another holder. An emulator takes the lowest free console port, so a stopped emulator must lose its serial, and a slow discovery must not undo a newer one. The serial in a lease can be old when the reaper takes it back, and `on_void` is the hook that ends instances. | Let the holder report the serial, for example with `touch --serial`. The serial is then known also while discovery cannot see the instance, but banksman acts on an address that it cannot check. |
| 50 | `ANDROID_SERIAL` | `run` and the hooks set `ANDROID_SERIAL` for a kind with an Android preset: the serial of the lease, or `banksman-serial-unknown`, which no device has, while the serial is not known. For other kinds, `run` keeps the value of the caller. Hooks never get the value of the caller | `adb` without `-s` and the connected tests of the Android Gradle plugin use this variable, so a tool that a script calls without the serial acts on the leased device. Without the variable, such a tool chooses a device itself, which can be the device of another holder; with the value that no device has, it fails with "device not found". A hook runs in the environment of whichever command reaps, which can be a command of another lease. | Leave the variable unset while the serial is not known. A tool then chooses a device itself. Or let each kind name its variable in the configuration, so that `run` has no rule for the presets. |
